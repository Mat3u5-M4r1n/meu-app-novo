Central de Ajuda

Manual prático de uso do Bling LINK Operacional

1

Navegando pelo Kanban

O Kanban é a tela principal do sistema. Ele organiza todos os clientes em colunas que representam a fase atual da implantação. Cada cartão representa um cliente.

Como mover um cartão de fase:

  1. Clique no cartão do cliente para abrir o modal de detalhes.
  2. Vá até a aba Implantação.
  3. Altere o campo Status para a nova fase desejada.
  4. Clique em Salvar. O cartão se moverá automaticamente para a coluna correta.

Dica: Você também pode usar o botão de status diretamente no topo do cartão no Kanban para uma mudança rápida de fase.

img/help-kanban-mover.png

O que significa cada coluna:

AgendadaSessão de implantação marcada — cliente tem data e horário confirmados.
Aguardando AgendaLink de agendamento enviado, mas o cliente ainda não escolheu o horário.
Em AndamentoSessão em curso ou encerrada, aguardando envio da gravação e anotações.
Enviar GravaçãoA sessão ocorreu; falta enviar o link da gravação para o cliente.
ReagendadoCliente solicitou nova data. Um reagendamento foi registrado.
ConcluídoImplantação finalizada com sucesso. Processo encerrado.
Estorno / CanceladoProcesso cancelado. Pode haver solicitação de reembolso em andamento.
2

Criando um Novo Registro

Para adicionar um novo cliente à base:

  1. Clique no botão + Novo Registro, localizado na barra superior do Kanban (canto superior direito).
  2. Preencha os campos obrigatórios: Nome da empresa e Implantador.
  3. Preencha os demais campos conforme as informações disponíveis.
  4. Clique em Salvar. O novo cartão aparecerá na coluna correspondente ao status selecionado.
img/help-novo-registro.png
3

Editando Dados de um Cliente

Clique sobre qualquer cartão do Kanban ou linha da Planilha para abrir o painel de detalhes. O painel é dividido em abas:

ContatoEmpresa, CNPJ, WhatsApp, e-mails, cidade, plano e valor.
ImplantaçãoStatus (fase no Kanban), implantador responsável, datas de agenda e links de acesso.
Infos Pré/PósInformações colhidas antes da sessão e registros pós-atendimento.
Reagenda/EstornoRegistrar solicitações de remarcação ou reembolso, com contadores automáticos.
ConexõesRelacionamentos do cliente com outros times (Loja Virtual, etc.).
Outro TimeVisualiza dados do mesmo CNPJ registrados pela outra equipe (IG ↔ BLV).

💡 Dica: O painel direito exibe a linha do tempo de notas — registre interações, observações ou pendências com contexto de data e autor. As notas ficam visíveis para toda a equipe.

Documentação Técnica

Arquitetura, segurança e integrações do Bling LINK

Admin Only
1

Visão Geral — O que o sistema faz

O Bling LINK Operacional é uma aplicação web interna desenvolvida para o time de Implantação da Bling. Seu objetivo é centralizar o acompanhamento de clientes em processo de implantação do sistema Bling (ERP/e-commerce), substituindo planilhas manuais por um sistema colaborativo em tempo real.

O sistema gerencia dois times distintos com bases de dados separadas:

  • IG (Implantação Guiada): Clientes do plano com acompanhamento humano direto.
  • BLV (Bling Loja Virtual): Clientes com foco em implantação de loja virtual.
img/docs-visao-geral.png — Diagrama geral da arquitetura
2

Stack de Tecnologias

O sistema usa tecnologias modernas, gratuitas ou de baixo custo, e não depende de grandes infraestruturas. Aqui está o que roda por trás:

Frontend

HTML + CSS (Tailwind via CDN) + JavaScript puro. Sem frameworks como React ou Vue — roda direto no navegador.

Backend

Node.js com Express. Serve os arquivos estáticos e expõe uma API REST que o frontend consome. Roda localmente na porta 3000.

Banco de Dados

Supabase (PostgreSQL na nuvem). Armazena todos os registros de clientes, atividades e projetos. Também gerencia a autenticação de usuários.

Bibliotecas adicionais instaladas no servidor:
  • helmet — Adiciona cabeçalhos de segurança HTTP em todas as respostas.
  • cors — Controla quais origens podem chamar a API.
  • express-rate-limit — Limita a quantidade de requisições por IP para evitar abuso.
  • @supabase/supabase-js — SDK oficial do Supabase para Node.js e para o navegador.
  • PapaParse — Lê e interpreta arquivos CSV para importação de planilhas.
3

Como o Frontend e o Backend se comunicam

Toda a comunicação entre a tela do usuário e o servidor segue o padrão REST — o frontend faz chamadas HTTP para rotas específicas do servidor, e o servidor responde em JSON.

img/docs-diagrama-fluxo.png — Diagrama de fluxo de dados

O fluxo padrão de uma ação (ex: salvar um cliente) é:

  1. Usuário clica em Salvar no modal do cliente.
  2. O JavaScript chama a função apiFetch('/api/clientes/123', { method: 'PUT', body: ... }).
  3. A função apiFetch injeta automaticamente o token JWT do usuário no cabeçalho Authorization.
  4. O servidor Express recebe a requisição, valida o JWT com o Supabase, e verifica se o e-mail do usuário está na lista de acessos permitidos (RBAC).
  5. Se tudo estiver correto, o servidor executa a operação no banco (Supabase/PostgreSQL) usando o token do usuário — o que garante que as regras de RLS (Row Level Security) sejam aplicadas.
  6. O banco retorna os dados atualizados. O servidor responde com o JSON. O frontend atualiza a tela sem recarregar a página.
Principais rotas da API (server.js):
Método + RotaDescrição
GET /api/auth/meValida o JWT e retorna os dados do usuário logado (nome, role, times).
GET /api/clientesLista todos os clientes da IG.
POST /api/clientesCria um novo cliente IG.
PUT /api/clientes/:idAtualiza os dados de um cliente IG existente.
DELETE /api/clientes/:idRemove um cliente IG.
GET /api/clientes-blvLista todos os clientes da BLV.
GET /api/timeline-cnpj/:cnpjRetorna as notas combinadas de IG + BLV para um CNPJ.
GET /api/cross-lookup/:cnpjBusca dados do mesmo CNPJ nos dois times simultaneamente.
GET /api/projetosLista as solicitações internas.
GET /api/atividades-blvLista as atividades registradas pelo time BLV.
4

Segurança — Login, Proteção de Rotas e Banco de Dados

Autenticação via Magic Link (Supabase Auth)

Em vez de senha, o sistema usa um Magic Link enviado por e-mail. O fluxo é:

  1. Usuário informa o e-mail na tela de login e clica em Enviar Link de Acesso.
  2. O Supabase envia um e-mail com um link único e temporário (expira em 1 hora, uso único).
  3. Ao clicar no link, o Supabase valida o token e redireciona o usuário para http://localhost:3000 com um JWT (JSON Web Token) na URL.
  4. O JavaScript do app detecta automaticamente o token da URL, estabelece a sessão e a armazena no sessionStorage do navegador (apagado ao fechar a aba).
  5. O app verifica com o backend (GET /api/auth/me) se o e-mail está na lista de usuários autorizados.

RBAC — Controle de Acesso por Perfil

O sistema possui dois perfis de usuário, definidos diretamente no server.js. Qualquer e-mail não listado recebe um erro 403 (acesso negado) mesmo que consiga se autenticar no Supabase:

PerfilE-mails autorizadosTimesAcesso extra
adminmateus.marin@bling.com.brIG + BLVAjustes, Documentação, todas as rotas
agentmanuela.curti@bling.com.br
luan.cavalheiro@bling.com.br		IG ou BLVMódulos operacionais do seu time

RLS — Segurança no Nível do Banco de Dados

O Supabase tem um mecanismo chamado Row Level Security (RLS). Funciona assim: mesmo que alguém descubra a URL do banco de dados, ele não consegue ler ou escrever dados sem um JWT válido de um usuário autenticado.

Quando o servidor faz uma operação no banco, ele usa o JWT do usuário (não uma chave de serviço global). Isso significa que o banco verifica individualmente se aquele usuário específico pode executar aquela operação — uma camada extra de proteção, independente do código do servidor.

⚠️ Tabelas protegidas por RLS: clientes, clientes_blv, atividades_loja_virtual, gestao_projetos. Todas exigem autenticação para leitura e escrita.
5

Integrações e API — Como sistemas externos enviam dados

Sistemas externos como o Octadesk, Jestor ou qualquer automação (n8n, Zapier, Make) podem criar e atualizar registros no Bling LINK via chamadas HTTP à nossa API. Para isso é necessário um token de serviço (JWT de um usuário admin).

img/docs-integracao-fluxo.png — Diagrama de integração externa

Exemplo: Criar um cliente IG via API externa

POST http://localhost:3000/api/clientes 
{
  "empresa": "Empresa Exemplo LTDA",
  "cnpj": "12.345.678/0001-90",
  "nomeContato": "João Silva",
  "whatsapp": "51999990000",
  "emailDaEmpresa": "contato@empresa.com.br",
  "emailDaAgenda": "joao@empresa.com.br",
  "cidade": "Porto Alegre",
  "estado": "RS",
  "plano": "Premium",
  "valorIG": 299.00,
  "status": "Agendada",
  "implantador": "Manu",
  "agenda": "2026-09-15 14:00 - 15:30"
}
Header obrigatório: Authorization: Bearer <JWT_TOKEN>

Exemplo: Registrar uma atividade BLV

POST http://localhost:3000/api/atividades-blv 
{
  "empresa": "Empresa Exemplo LTDA",
  "titulo": "Follow-up pós-implantação",
  "followup": "Cliente reportou dúvida sobre emissão de NF-e. Orientamos e enviamos tutorial.",
  "criadoPor": "Luan Cavalheiro"
}

Exemplo: Atualizar o status de um cliente IG

PUT http://localhost:3000/api/clientes/1234 
{
  "status": "Concluído",
  "igRealizada": "Sim",
  "informacoesPos": "Implantação concluída. Cliente apto para uso autônomo."
}
Respostas da API:
  • 200 / 201 — Operação bem-sucedida. Retorna o objeto JSON atualizado.
  • 400 — Dados inválidos no corpo da requisição.
  • 401 — Token JWT ausente, inválido ou expirado.
  • 403 — E-mail do token não está na lista de acessos permitidos.
  • 404 — Registro não encontrado.
  • 429 — Limite de requisições atingido (rate limit: 500 req/min para API geral).
  • 500 — Erro interno do servidor.
